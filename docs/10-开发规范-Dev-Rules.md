## §1 概述

### 1.1 文档定位

本文档是 AI MALF RiskBench v0.02 的**开发流程唯一权威**，规定从任务启动到交付的 16 步标准化流程、TDD 纪律、单一任务门禁、.plan/.record 双目录治理、Git 纪律与文档治理检查。

本规范继承 v0.01 workflow.md 的 TDD 三步与收尾流程，并参考 pi-studybuddy 10-Dev-Rules 的 16 步结构与治理范式，结合 v0.02 的 pi 底座 + Electron 壳 + Adapter 桥接特点形成。

**适用范围**：
- v0.02 主仓 `Z:\pi-malf-riskbench-v0.02` 全部业务代码施工

- v0.01 组件继承时的 Adapter 桥接施工

**不适用范围**：
- v0.01 已实现组件（290 passed）的内部修改——继承不重写
- MALF v2.1 领域权威定义——只读不改写
- 纯文档治理修复（无业务代码变更时走简化流程）

### 1.3 流程铁律四条

| 编号 | 铁律 | 含义 | 违反后果 |
|---|---|---|---|
| **铁律 1** | 未授权不施工 | 步骤 5（计划批准）与步骤 16（提交交付）是两个用户授权节点；未经授权不得写业务代码、不得提交推送 | 立即停止，回退到上一授权节点 |
| **铁律 2** | 单一任务执行 | `.plan/` 同一时刻只允许一份执行中计划；未选任务不得预写文件清单/命令/预期输出 | 拒绝创建新计划，提示用户先完成当前任务 |
| **铁律 3** | TDD 先行 | 先写与权威条款对应的失败测试（RED），再写最小实现使其通过（GREEN），最后重构（REFACTOR） | 禁止先实现再补测试；禁止用待测实现自动生成 golden 预期 |
| **铁律 4** | 文档同步 | 任务完成后必须更新 04-Todo（任务完成 + 事实 + 提交号）并创建 .record 实施记录；文档治理检查必须通过 | 不得视为完成；不进入下一任务 |

│  pending                      │  in_progress                   │  testing → done               │
├───────────────────────────────┼────────────────────────────────┼───────────────────────────────┤

## §3 16 步详解（每步含：目标/操作/产出/失败处理）

### 3.1 准备阶段（步骤 1-5）

#### 步骤 1：读文档定边界

| 项 | 内容 |
|---|---|
| **目标** | 建立完整上下文，明确当前任务的边界与权威依据 |
| **操作** | 按以下顺序读取文档：<br>1. `AGENTS.md`（待创建）—— 系统身份 + 权威链 + 任务铁律<br>2. `docs/00-文档索引-Index.md` —— 文档导航 + 门禁状态 + 当前状态总览<br>3. `docs/04-任务清单-Todo-List.md` —— 当前任务注册表 + 里程碑状态<br>4. `.plan/00-当前任务.md`（若存在）—— 唯一执行中任务计划<br>5. 相关设计文档（依据任务范围）—— 01-TRD / 02-PRD / 03-Arch / 05-ERD / 06-API / 07-Workflow / 08-Test / 09-UI |
| **产出** | 上下文建立确认；任务边界与权威依据明确 |
| **失败处理** | 若上述文件缺失、相互冲突或当前任务不明确 → **停止业务施工**，只允许修复治理文档或请求用户裁决 |

#### 步骤 2：检查文档门禁

| 项 | 内容 |
|---|---|
| **目标** | 确认任务已合法登记，.plan/ 单一执行，文档无冲突 |
| **操作** | 三项检查（必须全部通过）：<br>1. **任务已登记**：当前任务已在 `docs/04-任务清单-Todo-List.md` 登记任务行（含 task-id、里程碑、状态）<br>2. **.plan/ 单一执行**：`.plan/` 目录无其他执行中计划（`00-当前任务.md` 不存在或已标记完成）<br>3. **文档无冲突**：04-Todo 任务状态与 .plan/ 一致；06-API 契约与代码无冲突；12-目录治理与实际目录无冲突 |
| **产出** | 门禁通过确认；若不通过则列出具体冲突项 |
| **失败处理** | 若任务未登记 → 先在 04-Todo 登记，不能直接写业务代码<br>若 .plan/ 有其他执行中计划 → 等待当前任务完成或用户裁决<br>若文档冲突 → 修复冲突后重新检查，不绕过 |

#### 步骤 3：编写 .plan/ 计划

| 项 | 内容 |
|---|---|
| **目标** | 编写唯一执行中任务计划，明确范围、文件、命令、预期输出 |
| **操作** | 创建 `.plan/00-当前任务.md`，包含以下章节：<br>1. **任务范围**：task-id、里程碑、目标、边界（做什么/不做什么）<br>2. **文件清单**：将修改/创建的文件列表（含路径）<br>3. **命令**：将执行的验证命令（type-check / build / test / smoke）<br>4. **预期输出**：每条命令的预期结果（通过/失败/数值）<br>5. **测试数据隔离**：测试运行数据路径 `Z:\pi-malf-riskbench-v0.02-runtime\runs\<task-id>\`<br>6. **权威依据**：引用的设计文档条款（03-Arch / 06-API / 08-Test 等） |
| **产出** | `.plan/00-当前任务.md` 完整计划文件 |
| **失败处理** | 若计划无法明确文件清单或命令 → 说明任务边界不清晰，回到步骤 1 重新读文档<br>若计划涉及未在 04-Todo 登记的范围 → 先更新 04-Todo，再写计划 |

#### 步骤 4：独立审查计划

| 项 | 内容 |
|---|---|
| **目标** | 自检计划完整性，检查与权威文档的偏差 |
| **操作** | 1. **自检**：计划是否包含全部 6 个章节；文件清单是否完整；命令是否覆盖 type-check/build/test/smoke；预期输出是否具体可验证<br>2. **偏差检查**：计划是否与 03-Arch 架构设计一致；是否与 06-API 契约一致；是否与 08-Test 测试要求一致；是否违反安全不变量六条；是否违反 v0.01 继承边界（继承不重写） |
| **产出** | 自检通过确认 + 偏差修正（若有） |
| **失败处理** | 若自检不通过 → 修正计划后重新自检<br>若发现偏差 → 修正计划以符合权威文档，不修改权威文档来迁就计划 |

#### 步骤 5：★ 用户批准计划（授权节点 1）

| 项 | 内容 |
|---|---|
| **目标** | 获取用户对计划的明确批准，进入执行阶段 |
| **操作** | 1. 向用户展示 `.plan/00-当前任务.md` 计划摘要（任务范围 + 文件清单 + 命令 + 预期输出）<br>2. 明确请求用户批准："请审查并批准此计划，批准后将进入执行阶段"<br>3. 等待用户明确批准（"批准"/"同意"/"开始"等明确指令） |
| **产出** | 用户明确批准确认 |
| **失败处理** | 若用户要求修改 → 回到步骤 3 修改计划，重新走步骤 4-5<br>若用户未明确批准 → **不得进入执行阶段**，等待用户指示<br>若用户拒绝 → 停止，不写任何业务代码 |

### 3.2 执行阶段（步骤 6-11）

#### 步骤 6：拆分实现（小步增量）

| 项 | 内容 |
|---|---|
| **目标** | 将任务拆分为小步增量，每步可独立验证 |
| **操作** | 1. 按计划文件清单拆分实现步骤（每步对应一个文件或一个功能点）<br>2. 每步实现后立即自查：是否符合 03-Arch 架构；是否违反安全不变量六条；是否与 06-API 契约一致<br>3. 小步增量提交到工作区（不 git commit，仅工作区修改） |
| **产出** | 小步增量代码（每步可独立验证） |
| **失败处理** | 若某步实现与计划不符 → 记录偏差，继续或回到步骤 3 修正计划<br>若发现计划遗漏文件 → 补充计划文件清单，记录偏差<br>若违反安全不变量 → 立即停止，修正实现 |

#### 步骤 7：编写测试（TDD RED → GREEN → REFACTOR）

| 项 | 内容 |
|---|---|
| **目标** | 按 TDD 三步编写测试与实现 |
| **操作** | 1. **RED**：先写与权威条款（03-Arch / 06-API / 08-Test / MALF v2.1）对应的失败测试；运行测试确认失败<br>2. **GREEN**：只写使当前测试通过的**最小实现**；运行测试确认通过<br>3. **REFACTOR**：测试保持通过的前提下整理结构（命名/提取函数/消除重复） |
| **产出** | 测试代码 + 实现代码（RED → GREEN → REFACTOR 完成） |
| **失败处理** | 若 RED 未失败 → 测试无意义，重写测试使其真正验证权威条款<br>若 GREEN 无法通过 → 实现有误，修正实现（不修正测试来迁就实现）<br>若 REFACTOR 后测试失败 → 回退重构，重新走 GREEN |

#### 步骤 8：type-check（tsc --noEmit）

| 项 | 内容 |
|---|---|
| **目标** | TypeScript 类型检查通过 |
| **操作** | 执行 `pnpm tsc --noEmit`（或项目配置的 type-check 命令） |
| **产出** | type-check 通过（无类型错误） |
| **失败处理** | 若有类型错误 → 修正类型定义或实现，重新执行直到通过<br>若错误来自 v0.01 继承代码 → 不修改继承代码，检查 Adapter 桥接类型是否正确 |

#### 步骤 9：build（pnpm build）

| 项 | 内容 |
|---|---|
| **目标** | 构建通过 |
| **操作** | 执行 `pnpm build`（或项目配置的 build 命令） |
| **产出** | build 通过（产物生成） |
| **失败处理** | 若 build 失败 → 根据错误信息修正，重新执行直到通过<br>若失败来自依赖缺失 → 检查 package.json 依赖，不引入未批准的依赖 |

#### 步骤 10：test（vitest + pytest）

| 项 | 内容 |
|---|---|
| **目标** | 全部测试通过（TS 层 vitest + Python 层 pytest） |
| **操作** | 1. 执行 TS 层测试：`pnpm test`（vitest）<br>2. 执行 Python 层测试：`pytest`（若涉及 MALF 引擎 / Adapter）<br>3. 确认全部通过，无跳过、无忽略 |
| **产出** | vitest + pytest 全绿 |
| **失败处理** | 若测试失败 → 修正实现或测试（遵循 TDD 纪律），重新执行直到全绿<br>若 v0.01 继承测试失败 → 不修改继承测试，检查 Adapter 是否破坏了继承契约 |

#### 步骤 11：smoke/E2E（系统冒烟 + 受影响 E2E + 安全不变量六条）

| 项 | 内容 |
|---|---|
| **目标** | 系统冒烟通过 + 受影响 E2E 通过 + 安全不变量六条断言通过 |
| **操作** | 1. **系统冒烟**：启动 Electron 应用，验证主流程可用<br>2. **受影响 E2E**：运行与本次修改相关的 E2E 测试<br>3. **安全不变量六条**（详见 03-Arch + 08-Test §5.7）：<br>　- INV-01 renderer 沙箱 `sandbox:true`<br>　- INV-02 严格 CSP（script-src/connect-src 限制）<br>　- INV-03 preload 受控桥接（不暴露 Node API）<br>　- INV-04 credential-vault safeStorage（Windows DPAPI 加密）<br>　- INV-05 Host RPC 契约（所有跨进程通信走 contract）<br>　- INV-06 HTML 预览独立 CSP（回测报告/Markdown 渲染隔离）<br>4. **确定性验证**（若涉及 MALF 引擎）：lineage_hash SHA256 跨机器可重现 |
| **产出** | smoke/E2E 通过 + 安全不变量六条断言通过 |
| **失败处理** | 若冒烟失败 → 根据错误修正实现，重新走步骤 6-11<br>若 E2E 失败 → 修正实现或更新 E2E（若合同变更且经批准）<br>若安全不变量失败 → **立即停止**，安全不变量不可妥协 |

### 3.3 收尾阶段（步骤 12-16）

#### 步骤 12：独立审查修复（diff 检查 + 偏差修正）

| 项 | 内容 |
|---|---|
| **目标** | 审查全部修改，修正偏差 |
| **操作** | 1. **diff 检查**：审查 `git diff` 全部修改，确认每处修改都有计划依据<br>2. **偏差修正**：对比计划与实际修改，记录偏差（计划遗漏/计划外修改/实现与计划不符）<br>3. **安全复查**：确认无密钥泄漏、无日志明文、无路径逃逸、无 v0.01 继承代码被修改 |
| **产出** | diff 检查通过 + 偏差记录 |
| **失败处理** | 若发现计划外修改 → 评估是否合理，合理则补充计划记录，不合理则回退修改<br>若发现安全问题 → 立即修正，重新走步骤 8-11 |

#### 步骤 13：更新 04-Todo + 文档

| 项 | 内容 |
|---|---|
| **目标** | 更新任务状态、事实、提交号；创建实施记录 |
| **操作** | 1. **更新 04-Todo**：标记任务完成；记录关键事实（实现内容/测试结果/偏差）；记录提交号（步骤 16 后回填）<br>2. **创建 .record 实施记录**：创建 `.record/T-<里程碑>-<序号>-实施记录.md`（详见 §8），包含 8 个章节<br>3. **更新 API 契约**（若 API 合同变化）：更新对应 spec 文档（06-API）<br>4. **更新计划完成状态**：在 `.plan/00-当前任务.md` 标明完成状态；保留该计划原件作为历史范围与验收证据 |
| **产出** | 04-Todo 更新 + .record 实施记录创建 + API 契约更新（若需） |
| **失败处理** | 若 04-Todo 更新失败 → 检查文档格式，不跳过<br>若 API 契约需更新但未更新 → 必须更新后才算完成 |

#### 步骤 14：文档治理检查（check-docs-governance.mjs）

| 项 | 内容 |
|---|---|
| **目标** | 文档治理检查通过 |
| **操作** | 执行 `node scripts/check-docs-governance.mjs`（待创建），检查：<br>1. 00-索引文档登记表与实际文件一致<br>2. 04-Todo 任务状态与 .plan/ 一致<br>3. 06-API 契约与代码 handlers 一致（AST 校验）<br>4. 12-目录治理与实际目录一致<br>5. 版本历史与实际变更一致 |
| **产出** | 文档治理检查通过 |
| **失败处理** | 若检查失败 → 根据报告修正文档，重新执行直到通过<br>若检查脚本不存在 → 按 §8 与 00-索引 §7.2 手动核对 |

#### 步骤 15：diff 检查（只提交本 session 改的文件）

| 项 | 内容 |
|---|---|
| **目标** | 确认提交范围只含本 session 改的文件 |
| **操作** | 1. 执行 `git status` 查看全部修改<br>2. 逐一核对：每个修改文件是否属于本任务计划范围<br>3. 排除：密钥/.env/完整 UUID/node_modules/venv/试炼场代码/运行数据（详见 §9.6 不提交清单）<br>4. 排除：其他 session 的遗留修改（若有，提示用户裁决） |
| **产出** | 提交范围确认（只含本 session 改的文件） |
| **失败处理** | 若发现非本 session 修改 → 不提交这些文件，提示用户裁决<br>若发现敏感文件 → 绝不提交，从工作区移除 |

#### 步骤 16：★ 提交交付（授权节点 2）

| 项 | 内容 |
|---|---|
| **目标** | 显式 git add + commit + 用户授权后推送 |
| **操作** | 1. **显式 git add**：按步骤 15 确认的范围，逐文件 `git add <file>`（禁止 `git add -A` 或 `git add .`）<br>2. **commit**：按 §9.4 commit message 格式提交<br>3. **请求用户授权推送**：向用户展示 commit 摘要，明确请求"是否推送到远程？"<br>4. **用户授权后 push**：执行 `git push`（或 `git push -u origin <branch>` 若新分支）<br>5. **回填提交号**：将 commit hash 回填到 04-Todo 和 .record |
| **产出** | commit 完成 + 用户授权后 push 完成 + 提交号回填 |
| **失败处理** | 若用户未授权推送 → 只 commit 不 push，等待用户指示<br>若 push 失败（远程变更） → 提示用户先 `git pull --rebase`，不 force push<br>若用户拒绝提交 → 保留工作区修改，等待用户指示 |

## §4 中断恢复

### 4.1 恢复规则

**铁律**：任何开发会话中断后恢复时，**必须重读 `.plan/00-当前任务.md`**，禁止凭聊天记忆继续施工。

### 4.2 恢复流程

```
1. 读取 .plan/00-当前任务.md
   │
   ├─ 若文件存在且标记"执行中" → 从计划记录的当前步骤继续
   │   1. 读取计划中的"当前步骤"标记
   │   2. 读取 .record/（若已创建）了解已完成内容
   │   3. 从当前步骤继续执行
   │
   ├─ 若文件存在且标记"完成" → 任务已完成，等待用户选择下一任务
   │
   ├─ 若文件不存在 → 无执行中任务，等待用户明确选择任务
   │
   └─ 若文件存在但与 04-Todo 状态冲突 → 停止，请求用户裁决
```

### 4.3 禁止事项

- **禁止**凭聊天记忆判断任务进度
- **禁止**跳过 .plan/ 直接写代码
- **禁止**在中断恢复时创建新任务计划（必须先完成或显式放弃当前任务）
- **禁止**用"我记得之前做到 XX"作为继续施工的依据

## §7 TDD 纪律

### 7.1 TDD 三步

| 步骤 | 名称 | 操作 | 纪律 |
|---|---|---|---|
| 1 | **RED** | 先写与权威条款对应的失败测试 | 测试必须对应权威条款（03-Arch / 06-API / 08-Test / MALF v2.1），不是凭空臆造 |
| 2 | **GREEN** | 只写使当前测试通过的**最小实现** | 不写超出当前测试需求的代码；不过度设计 |
| 3 | **REFACTOR** | 测试保持通过的前提下整理结构 | 重构不改变行为；重构后必须重新运行测试确认通过 |

### 7.2 TDD 流程图

```
写失败测试（RED）
    │
    ├─ 运行测试 → 失败 ✓ → 进入 GREEN
    │
    └─ 运行测试 → 通过 ✗ → 测试无意义，重写测试

写最小实现（GREEN）
    │
    ├─ 运行测试 → 通过 ✓ → 进入 REFACTOR
    │
    └─ 运行测试 → 失败 ✗ → 修正实现（不修正测试来迁就实现）

重构（REFACTOR）
    │
    ├─ 运行测试 → 通过 ✓ → 完成
    │
    └─ 运行测试 → 失败 ✗ → 回退重构，重新走 GREEN
```

### 7.3 禁止事项

| 编号 | 禁止 | 理由 |
|---|---|---|
| TDD-禁 1 | **禁止先实现再补测试** | 先实现后补的测试只会验证"实现做了什么"，而非"应该做什么" |
| TDD-禁 2 | **禁止用待测实现自动生成 golden 预期** | 用实现产出作为预期值，等于"实现验证实现"，无法发现实现错误 |
| TDD-禁 3 | **禁止仅以覆盖率百分比验收** | 覆盖率高不等于测试有效；必须验证测试是否对应权威条款 |

### 7.4 测试数据隔离

| 类型 | 路径 | 用途 |
|---|---|---|
| **v0.02 测试运行数据** | `Z:\pi-malf-riskbench-v0.02-runtime\runs\<task-id>\` | v0.02 所有测试写入此目录 |
| **v0.01 测试临时目录** | `Z:\ai-malf-riskbench--runtime\tmp\` | v0.01 继承测试仍可用 |
| **真实业务数据根** | `Z:\ai-malf-riskbench-data\` | **绝不污染**——只读访问 |

**铁律**：所有测试写 `Z:\pi-malf-riskbench-v0.02-runtime\runs\<task-id>\`，绝不污染真实业务数据根 `Z:\ai-malf-riskbench-data\`。

## §9 Git 纪律

### 9.1 分支命名

**格式**：`<executor>/<work-id>-<scope>`

| 字段 | 含义 | 示例 |
|---|---|---|
| `<executor>` | 执行者标识 | `agent` / `user` |
| `<work-id>` | 任务 ID | `T-M0-001` |
| `<scope>` | 任务范围简述 | `electron-skeleton` / `malf-adapter` / `risk-declare` |

**示例**：`agent/T-M0-001-electron-skeleton`

### 9.2 合并规则

| 操作 | 规则 |
|---|---|
| 合并方式 | `git merge --ff-only`（仅快进合并） |
| 主分支 | `master`（受保护，不直接 push） |
| 合并前提 | 步骤 11 smoke/E2E 通过 + 步骤 14 文档治理检查通过 |

### 9.3 禁止操作

| 编号 | 禁止 | 理由 |
|---|---|---|
| Git-禁 1 | `git reset --hard` | 丢失工作区修改 |
| Git-禁 2 | `git clean -fd` | 删除未跟踪文件 |
| Git-禁 3 | `git stash` | 暂存易遗忘，违反单一任务门禁 |
| Git-禁 4 | `--no-verify` | 跳过 pre-commit 钩子 |
| Git-禁 5 | `git add -A` / `git add .` | 可能提交敏感文件或非本 session 修改 |
| Git-禁 6 | `git push --force` / `--force-with-lease` | 覆盖远程历史（除非用户明确要求且非主分支） |

### 9.4 commit message 格式

**格式**：`type(scope): 中文描述`

| 字段 | 可选值 | 示例 |
|---|---|---|
| `type` | `feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `build` / `ci` | `feat` |
| `scope` | 受影响模块 | `malf-adapter` / `electron-main` / `risk-declare` |
| `中文描述` | 简明描述变更 | `实现 MALF Python 引擎 Adapter 桥接` |

**示例**：
- `feat(electron-main): 实现 Electron 主进程五件骨架`
- `fix(malf-adapter): 修复 44 字段契约透传缺失 rule_versions`
- `test(risk-declare): 补充风险声明状态机边界测试`
- `docs(04-todo): 标记 T-M0-001 完成`

### 9.5 完成判据

任务完成必须**三者齐全**：

| 判据 | 证据位置 | 要求 |
|---|---|---|
| 1. docs/04 证据 | `docs/04-任务清单-Todo-List.md` | 任务标记完成 + 事实 + 提交号 |
| 2. master 复验 | 本地 master 分支 | 代码已合并到 master 且通过全部测试 |
| 3. origin/master 推送 | 远程 origin/master | 代码已推送到远程 |

### 9.6 不提交清单

以下文件**绝不提交**到 Git：

| 类型 | 示例 | 理由 |
|---|---|---|
| 密钥 | `.env` / `auth.json` / `credentials.json` / `*.key` | 安全风险 |
| 完整 UUID | 含完整 UUID 的配置文件 | 隐私风险 |
| node_modules | `node_modules/` | 可重新安装 |
| venv | `venv/` / `.venv/` | 可重新创建 |
| 试炼场代码 | `Z:\pi-malf-riskbench-v0.02-composer\*` | 试炼场不进 Git |
| 运行数据 | `Z:\pi-malf-riskbench-v0.02-runtime\*` | 运行时数据可重生 |
| 生产数据库 | `Z:\ai-malf-riskbench-data\*` | 业务数据根，不进 Git |
